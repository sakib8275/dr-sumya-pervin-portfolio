## ⚠️ Mistakes made this session — do not repeat

I produced **three** confident, wrong assessments of the leaked token's power before the operator
read the scope off the dashboard. Each came from inferring a credential's reach from indirect
signals:

| Inference | Why it was wrong |
|---|---|
| Empty `/accounts` + `/zones` → "narrow token" | A Turnstile-scoped token simply doesn't grant account listing. Empty says nothing about power. |
| `cfut_` prefix → "R2 API token, assume All buckets Admin R&W" | Taken from one line in an R2 doc. `cfut_` is Cloudflare's modern prefix for API tokens generally. |
| R2 S3 `AccessDenied` → "recognised but unpermissioned" | A controlled retest showed a **deliberately wrong secret returns the identical `AccessDenied`**. It cannot distinguish authz failure from a bad signature. |

**Rule: read a credential's scope off the dashboard. Never infer it from error codes or token
prefixes.** The operator's one-line answer settled in seconds what ~$40 of API probing did not.

This is a specific instance of playbook rule 1 (*"a status code is not a result"*) — it applies
to API error codes, not just HTTP 200s.
