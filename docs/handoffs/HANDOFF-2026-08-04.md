## 4. ⚠️ The Telegram button never routed to the doctor — read this before "finishing" L6

The owner deferred Telegram integration. **That costs nothing today**, and the
reason is not obvious from the CMS, which presents a "Telegram Username /
Channel" field as if it were the WhatsApp field's twin.

It is not. `public/js/main.js:726`:

```js
const waNumber = (cmsConfig.whatsapp || '').replace(/[^0-9]/g, '');
const waUrl = waNumber ? 'https://wa.me/' + waNumber + '?text=' + waMsg : '';
const tgUrl = 'https://t.me/share/url?url=' + encodeURIComponent(window.location.href) + '&text=' + waMsg;
```

`tgUrl` **never reads `cmsConfig.telegram`.** `t.me/share/url` is Telegram's
generic share sheet: it opens the *patient's* Telegram and lets them forward the
message to anyone they like. It reaches the doctor only if the patient happens to
pick her. The stored `telegram` value is consumed in exactly one place —
`main.js:1144`, echoing it back into the CMS input.

So:

- **WhatsApp is properly wired** (`wa.me/<digits>`; FAB at `main.js:163`, booking
  button at `:725`) and L6 is genuinely closed on that half.
- **Telegram would need a code change, not just a username.** Supplying a real
  `@username` and building `https://t.me/<username>` is the actual fix.
- **Do not file the current behaviour as a bug** — it is deferred by the owner,
  recorded as such in `STATUS.md` and `HUMAN-TASKS.md` Task 6.

This is the second time in this repo a field has looked configured while driving
nothing. Treat "the value is stored" and "the value is used" as separate claims.

## 5. Observability on the digest — and why it went in *before* the first run

Facts: the worker deployed **2026-08-03 15:10 UTC**, after both of that day's
cron times (08:30 and 10:30 UTC). **No cron had ever fired.** First real run:
**2026-08-04 08:30 UTC / 14:30 Dhaka.**

The trap: production D1 holds **0 appointments**, and `runDigest` returns without
sending when there is nothing to report. So on the first run:

| What happened | What the operator sees |
|---|---|
| Worker never fired | no email |
| Fired, nothing to report, correctly sent nothing | no email |
| Fired, tried to send, failed | no email |

**Three different outcomes, one observation.** And the one mailbox that would
disambiguate — `dr.enamtalha@gmail.com` — is not readable from this repo. Without
logs the first run would have produced no evidence at all, and "no email" would
have been argued in both directions.

Added to `workers/digest/wrangler.toml`:

```toml
[observability]
enabled = true
head_sampling_rate = 1
```

`head_sampling_rate = 1` is deliberate — two invocations a day is nothing to
sample. Redeployed as version **`0f6d80cd-4485-444a-95ea-fce32f4139fe`**
(2026-08-03 22:16 UTC); both crons re-registered; confirmed on the *deployed
script* via the Cloudflare API (`logs.enabled true`, `persist true`,
`invocation_logs true`) rather than assumed from the file.

**The generalisation, for any future cron worker here:** a Worker whose only
trigger is a schedule and whose only output leaves the system has no observable
surface. Turn logs on when you deploy it, not after the first thing goes wrong —
by then the evidence you needed has already not been recorded.

## 6. Scheduling the follow-up: what does *not* work

The operator asked for the logs to be checked after the run. Both scheduling
routes have real limits, and they are worth knowing before someone tries again:

- **Cloud routines (`/schedule`) cannot do this.** They run in Anthropic's cloud
  with a fresh git checkout and only the account's claude.ai connectors. The only
  connector attached is **Google Drive** — there is no Cloudflare connector, and
  the local `wrangler`/MCP credentials do not exist there. A cloud agent would
  have woken up with no way to reach Cloudflare.
- **A local one-shot cron job (`ac8c8f45`, 14:47) was created instead, but it is
  session-only** — held in memory, gone when the CLI exits, and it only fires
  while the REPL is idle. Do not rely on it.

**The reliable path is a human asking an agent after 14:30 Dhaka.** That is why
the check is written up as the first task in the next session's prompt rather
than left to a timer.

## 8. Carry-forward gotchas

Everything in `-v4` §8 and `-v3` §9 still holds. Added by this session:

- **A stored setting is not a used setting.** Verify the consuming code path
  before calling a configuration task done (§4).
- **A cron-only Worker with an off-box output is invisible by default.** Enable
  observability at deploy time; "no output" is not a diagnosis (§5).
- **Cloud routines have no Cloudflare access on this account** — Google Drive is
  the only connector. Local cron jobs are session-only. Neither is a dependable
  way to check on production (§6).
- **Documentation goes stale when a *human* acts**, not only when code changes.
  Re-probe rows that depend on someone else's click before repeating them (§2).
- `wrangler d1 execute` prints only the `meta` block when the output is long
  enough to be truncated — re-run with `--json` and grep for `"results"` to see
  the rows.
