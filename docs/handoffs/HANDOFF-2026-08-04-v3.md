## Deploy 2 — `42aa5567`, F11 + a bug F10 caught

### The bug

`tests/e2e/whatsapp-gating.spec.mjs` asserted the WhatsApp FAB is hidden when no
number is configured. It failed — and the test was right.

`[hidden]` is only a UA rule (`display: none`), so **any** class setting `display`
outranks it. `.fab-btn { display: grid }` did exactly that, which means
`renderContactChannels()`'s `fab.hidden = !digits` (`main.js:164`) **hid
nothing**. With no WhatsApp number configured, the floating button still
rendered — as a live link to `href="#"`. That is precisely the "live link to
nobody" that the hardcoded `+880 1700-000000` placeholder created and that the
gating was written to remove. `#navTel` escaped only by luck: `.nav-tel` happens
to set no `display`.

Not visible in production today because a number *is* configured — it would have
returned the moment anyone cleared the field in CMS Settings.

Fixed with `[hidden] { display: none !important; }` in `public/css/style.css`.
Only two real `hidden` attributes exist in the markup (`#navTel`, `#fabWhatsapp`);
everything else is `aria-hidden`, so the global rule is safe. Verified live: a
freshly injected `<p hidden>` computes to `display: none` on the apex.

## F10 — the DOM layer

`tests/e2e/`, 14 tests, `npm run test:e2e`. Deliberately outside `npm test` so
the deploy gate stays ~3 s.

**The runner is not `wrangler pages dev`, and that is the main design decision.**
`verifyTurnstile` requires siteverify to return both the expected action and an
allowlisted hostname; `pages dev` cannot intercept that outbound call, so every
DOM-level booking test would 403 for a reason having nothing to do with the DOM.
`tests/helpers/harness.mjs` already solved this for the API suite with
Miniflare's `outboundService` — and Miniflare also listens on a real HTTP port.
So the specs drive a real Chromium against the real compiled Worker with real
D1/R2 and a stubbed siteverify. One stub, one migration path, one route table.

Turnstile is stubbed page-side via `addInitScript`. The stub derives its token
**from the widget's action** (`good:booking` / `good:login`): a single fixed
token would pass booking and silently 403 login.

Five areas: real pointer-click booking · XSS inert in the CMS · booking-failure
state · WhatsApp CTA gating · the pre-hydration submit guard. Plus the UX batch's
assertions per `docs/audits/UX-AUDIT-2026-08-04.md`.

**Two traps found while writing them, both now documented in `agent.md`:**

1. `.open-booking` has **seven** elements and which are visible depends on the
   viewport — the nav one is hidden below the desktop breakpoint, the drawer one
   above it. `.first()` silently picks a hidden element at 375px and times out.
   Use `openBookingModal(page)`, which goes through `:visible`.
2. A **past date cannot be used to test server rejection.** `main.js:653` sets
   `dateInput.min` to today, so the browser's native constraint validation stops
   the submit and no request is ever sent. Use a future **Friday** — passes every
   client check, refused by `functions/lib/schedule.js`.

**What F10 does not cover:** the zone-injected scripts (they exist only on the
apex) and a real Turnstile widget. Both stay live-apex checks at deploy time. It
also does not duplicate `tests/headers.test.mjs`, which already fails if an
`on*=` attribute reappears in `public/`; F10 proves the *behaviour* instead.
