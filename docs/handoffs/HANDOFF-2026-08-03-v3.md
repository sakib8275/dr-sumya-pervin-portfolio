### Two things done beyond the bug list

**The crons are derived, not typed.** `cronForChamber()` computes each cron from
`CHAMBERS` + `CUTOFF_MIN` (cutoff → UTC → day list), and a test fails if
`wrangler.toml` disagrees. Without this, changing a chamber's hours moves the
booking cutoff while the digest keeps mailing a list that is not yet final — a
silent, plausible-looking wrong answer. `cronForChamber` also throws if a cutoff
would cross UTC midnight, because the day-of-week list would then need shifting.

**`workers_dev = false`.** The Worker exports only `scheduled()`, so the
workers.dev hostname answered nothing and was pure surface. Probe now returns 404.

## 2. The cron discovery — read this before touching any schedule

**Cloudflare's schedules API rejects numeric day-of-week outright.** Tested live
against `/workers/scripts/dr-sumya-digest/schedules`:

| Cron | Result |
|---|---|
| `30 8 * * 0-3,6` | `10100: invalid cron string` |
| `30 8 * * 0,1,2,3,6` | `10100: invalid cron string` |
| `30 8 * * 0-3` | `10100: invalid cron string` |
| `30 8 * * 0-6` | `10100: invalid cron string` |
| `30 8 * * SUN-WED,SAT` | **accepted** |
| `30 8 * * SUN,MON,TUE,WED,SAT` | **accepted** |

The numeric crons came from the original scaffold and were described as "correct"
in both `HANDOFF-2026-08-03.md` and `docs/prompts/F8-DIGEST-PROMPT.md`. **They
could never have deployed.** Standard-cron intuition does not apply.

Deployed now: `30 8 * * SUN-WED,SAT` (DCIMCH, 14:30 Dhaka cutoff) and
`30 10 * * SUN-THU,SAT` (Alliance, 16:30 Dhaka cutoff).

**The failure mode is nastier than the error.** `wrangler deploy` uploads the
Worker, prints `Uploaded`, and *then* fails the trigger step. The first deploy
left a live Worker with **zero schedules** and an exit that looked half-successful.
Always read past `Uploaded` to the `schedule:` lines.

## 5. The L7 correction

`STATUS.md` claimed L7 was a "WAF rate-limit on `POST /api/auth/login` (5/min/IP,
Managed Challenge)". It is not. The zone actually has:

- a **custom firewall rule** `Login Rate Limit`: `managed_challenge` on every
  `POST /api/auth/login` — no counter, no threshold;
- one **rate-limiting rule**, `Leaked credential check`: block, 5 req/10 s, on
  `cf.waf.credential_check.password_leaked` — unrelated to brute-forcing.

The Free plan allows one rate-limiting rule, so a genuine 5/min login limit means
giving up leaked-credential blocking.

**Decision taken (the operator delegated it): keep the leaked-credential rule, fix
the documentation, do not swap.** Credential stuffing with known-leaked passwords
is the likelier attack against a single-PIN login; the managed challenge already
stops naive unattended brute-forcing, since a script has no clearance cookie; and
per-IP limiting is the wrong shape anyway — a real throttle belongs in the
application, keyed on the PIN attempt, where a rotating source IP cannot evade it.

**Open follow-up: an application-level login throttle in
`functions/api/auth/login.js`, backed by D1 or KV.** Not yet in the FIXPLAN.

## 9. Carry-forward gotchas (still true)

- Rollback target for the *site* is **`5423d45e`**; quote deployment ids only
  from `npx wrangler pages deployment list`, never memory.
- Secret checks by presence only (`[ -n "$VAR" ]`); never print or record the PIN.
- Turnstile widget hostnames are dashboard-only (OAuth API → 10405).
- Fixtures derive dates from `nextOpenDate(CHAMBER, addDays(dhakaParts().dateStr, 1))`

- Apex page size ≠ pages.dev page size (zone HTML rewriting). Compare by
  deployment id, not bytes.
- `wrangler deploy` for the digest must run **from `workers/digest/`**; the repo
  root `wrangler.toml` is the Pages project.
