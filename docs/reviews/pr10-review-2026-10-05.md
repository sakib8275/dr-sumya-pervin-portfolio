### S3 — Turning reduced motion on mid-visit while a dot is focused drops focus to `<body>`

Probed: focus `.jn-dot` (2), `page.emulateMedia({reducedMotion:'reduce'})` → the fallback removes `.jn-nav` from the DOM and focus falls to `BODY` (`document.activeElement` → `body`). Acceptable in the worst-case sense (no crash, no hidden focus trap), but better to move focus to a stable target — e.g. make `.nameplate` itself `tabindex="-1"` and focus it, or focus the eyebrow/list container — or at least document the behavior.

### S4 — Reduced-motion-off again mid-visit never re-enhances (undocumented one-way fallback)

Probed: RM on mid-visit → fallback runs → RM turned back off → 800ms later `.jn-live` 0, `.jn-nav` 0, no roledescription, no aria-live. The `change` listener at `public/js/site.js:104-114` only handles reduce turning on. Defensible (don't re-animate mid-session), but the PR body/STATUS describe the mid-visit fallback as a one-directional restoration without saying it is permanent for the session. Document it, or re-enhance on RM-off.

### S5 — Small APG carousel deltas

`site.js`'s dots use `aria-current="true"/"false"`; the APG *grouped* carousel pattern marks the current slide-picker button `aria-disabled="true"` (keeps it in the tab order, prevents accidental re-tap) — `aria-current` is common and not wrong, but the PR's deviation note only covers `role="group"`, not this. Also, APG asks that the rotation control (Pause) precede the rotating content in tab order; here the dots come first and Pause is appended last (`site.js:58-59`). Slide elements also lack `role="group"` + `aria-roledescription="slide"` and their own accessible names. None blocking; the slide content itself is the accessible name in practice.

## Rulings on the contested points

**R1 — Is the reduced-motion page really identical to the no-JS page in the hero?**
For layout and DOM state, **yes**. Probed at 1440: no-JS panel height = 725.875px, reduced-motion panel height = 725.875px (no-JS measured with `site.js` aborted; RM measured with RM emulated before load), all five steps visible in both, `aria-live`/roledescription null in both. The only divergence is the entrance *animation* treatment: RM substitutes a 240ms `fade-in` for the authored `panel-fill`/wipe sequence (`site.css:974`), while no-JS *with* motion allowed plays the authored sequence. No JS-gated or motion-gated CSS changes hero layout (the `.jn-live` rules are gated on the JS-added class only). So Qwen's Finding 1 is correctly closed on coverage terms (the real no-JS spec exists now), and the author's reply — "the reduced-motion page *is* the unenhanced list" — holds for layout/a11y state today. Keep the no-JS spec: if anyone later gates hero CSS on a JS class, only that spec notices.

**R2 — Is `role="group"` + a JS-only carousel roledescription acceptable under the APG carousel pattern?**
**Yes.** The APG carousel pattern states: "A carousel container element … has either role `region` or role `group`. The most appropriate role … depends on the information architecture." (`w3.org/WAI/ARIA/apg/patterns/carousel/`). `region` would add a landmark no visitor navigates to; `group` is the quieter reading for a five-line hero panel. Moving `aria-roledescription="carousel"` from static markup to enhance-time means the no-JS/reduced-motion state announces as a plain group, which matches what it renders as. The deviation note in the PR body is adequate. Two APG details it does *not* cover are in S5.
