**P1 — the `.card` hover lift stops animating, and the two card families are now *less* unified than before.** `public/css/site.css:352-353, 359`

Pre: `.card { … transition: transform .15s ease, box-shadow .15s ease; }` + `.card:hover { transform: translateY(-2px); }`.
Post (diff): `transition: border-color .15s var(--ease), box-shadow .15s var(--ease), scale var(--t-press) var(--ease-out);` with the lift moved to `translate: 0 -2px`. `translate` is **not** in the transition list, so the 2px lift now snaps in and out while colour and shadow still ease — the lift loses the only transition it had. `.h-learn-card` (741) did get `translate var(--t-press) var(--ease-out)`, so the two cards now differ in exactly the property the plan was written to unify, which fails the plan's own done-when ("both card families share one idiom", `plans/005-duration-tokens-card-idiom.md:91`).

The PR body records the defect without reading it as one: "hover+press compose verified frame-by-frame — **`translate` holds `-2px` in every frame**". A transitioned lift would not hold -2px in the first frames; holding it every frame *is* the snap. Nothing in the suite catches this (no motion test).

Root cause is in the plan, not the execution: plan's `.card` target (`:56-59`) omits `translate` from the transition list while its `.h-learn-card` target (`:83`) includes it. Fix is one clause on `.card`: `translate var(--t-press) var(--ease-out)` — interpolating from `translate: none` is already proven on this sheet by `.mega` (`:222-223`).

**P3 — the new comment asserts a false CSS invariant.** `site.css:356-360` ("`translate`, not transform, so it composes with the press's scale") and PR body ("the old `transform` lift would have replaced it")
Per CSS Transforms 2 the used value is translate·rotate·scale·transform, so `transform: translateY(-2px)` and `scale: .99` **already** compose — that is precisely what ships today at `:673` `.h-tier.rec { … transform: translateY(-10px); }` plus `:705` `:is(.h-tier, .pr-card, .pr-plan):has(.card-link:active) { scale: .99; }`. The only actual difference is order: under `transform` the press also scales the lift (−2px → −1.98px, −10px → −9.9px); under `translate` the offset stays exact. `translate` is still the better choice, but the comment states why in a way the next contributor will repeat wrongly — and the same wrong wording already sits at `:703-704`, so this diff halves rather than fixes it.
