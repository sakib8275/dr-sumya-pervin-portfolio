**[P1] public/css/site.css:262 — reduced-motion no longer suppresses the drawer OPEN animation (specificity hole introduced by this PR).**
Evidence: the PR adds a `transition` declaration to the higher-specificity state rule:
```css
.drawer.active { transform: none; visibility: visible; transition: transform .3s var(--ease-drawer), visibility 0s linear 0s; }
```
while the reduce block (post-apply site.css:1096–1097) only lists the base selector: `.drawer, .scrim, … .bk-form-fields { transition: none; }`.
Why it matters: a transition is started from the **after-change** style. Opening the drawer adds `.active`, so the effective transition comes from `.drawer.active` (0,2,0), which beats the RM list's `.drawer` (0,1,0) regardless of source order — under `prefers-reduced-motion: reduce` the drawer now slides in over 300 ms, breaking the block's own stated contract ("drop the movement, keep the state change") and the pre-PR behavior (before this PR `.drawer.active` declared no transition, so RM killed both directions). Closing stays instant under RM, so reduce users get an asymmetric slide-open/pop-close. Plan 011 asserted "`.drawer` is already in the reduced-motion `transition: none` list, so RM keeps the instant swap — no new RM work"; that claim is false for the open direction, and no e2e test opens the drawer under reduce (the RM mobile describe at tests/e2e/mobile-site.spec.mjs:130 covers the reel only), so `npm run test:e2e` stays green either way. The repo's own exemplar avoids this: `.mega` (site.css:223) declares `display … allow-discrete` transitions on the base rule only, and the RM block's `.mega { transition: none; }` therefore covers both directions.
Fix: add the state selector to the RM list — `.drawer, .drawer.active, .scrim, … { transition: none; }` — and ideally one assertion in the mobile RM spec (open drawer under `emulateMedia({ reducedMotion: 'reduce' })` and poll `getComputedStyle(drawer).transitionDuration === '0s'`), since `toBeVisible` cannot detect the slide.

**[P2] public/css/site.css:259–262 + public/js/site.js shut() — the new exit window keeps the closed drawer focusable, clickable, and exposed as `aria-modal="true"` for 300 ms.**
Evidence: `visibility 0s linear .3s` on the base rule deliberately holds `visibility: visible` through the slide-out, while `shut()` (site.js:168–174) does nothing about interactivity — it only removes `.active`, unfocus-traps, and focuses the burger. The drawer markup is `<div class="drawer" id="drawer" role="dialog" aria-modal="true" …>` (public/index.html:375).
Why it matters: pre-PR, closing made every drawer link un-focusable and un-clickable on the same frame. Post-PR, a keyboard user who presses Escape and Tabs within 300 ms can land on a nav link of a dialog the UI shows as closed (and that link becomes `visibility: hidden` under them mid-focus, dropping keyboard position); a tap that lands in the sliding panel still navigates. Bounded (300 ms) and only on the mobile drawer, but it is exactly the "invisible-but-focusable" class of state plan 011's own feel-check demanded not exist ("no invisible-but-focusable drawer"). The CSS cannot fix this; the two-line JS fix touches `open()`/`shut()`, which was a plan 006/011 boundary — that deviation is justified and should be recorded:
Fix: in `shut()` add `drawer.inert = true;` and in `open()` `drawer.inert = false;` (supported everywhere the drawer JS runs; keeps the visual exit untouched).

**[P3] public/js/site.js:412 — `.is-ink` is never removed outside a re-run, so it permanently overrides the first-reveal animation.**
Evidence: `if (rerun) { out.classList.remove('is-ink'); void out.offsetWidth; out.classList.add('is-ink'); }` — after the first re-run the class stays on the element forever, and `.tool-out.is-ink` (site.css:427, declared after `.tool-out:not([hidden]) { animation: rise-in … both; }` at :421, equal specificity) wins the cascade for the element's whole life. I verified no reachable breakage today: nothing re-hides the tool outputs (`grep '\.hidden'` shows `out.hidden = false` only in `show()`, plus `bk-err` toggles), and a page reload rebuilds the DOM. But the file's own comment at site.js:409 ("first reveal plays rise-in") silently stops being true on any future hide/show path or on a `display:none`→visible cycle (bfcache/print-style edge): the animation-name stays `re-ink` and a fresh element reveal replays the dip instead of the entrance.
Fix: make the branch symmetric — `if (rerun) { … } else { out.classList.remove('is-ink'); }` — or remove the class on the reveal path before setting `hidden = false`.

**[P3] public/css/site.css:438 — the `allow-discrete` fade-out was probed in one engine only; on the clinic's dominant mobile browser it is unverified.**
Evidence: `transition: opacity 200ms var(--ease-out), display 200ms allow-discrete;` — plan 006's status line records "per-frame probe: display holds through the fade" without naming a browser. Failure mode is graceful (an engine without `transition-behavior` discards the whole shorthand → today's instant swap, and the fieldset never un-hides so the missing `@starting-style` entry direction is unreachable), so this is not a defect — but iOS Safari is plausibly a large share of a Dhaka clinic's traffic, and the discrete-property flip point (hold-until-end vs 50 %) is engine-territory that the CSS comments assert as fact. One 10-second DevTools probe of `#sbFields` on a real iPhone/Safari (or a Playwright webkit project) before merge would make the comment true across the matrix. No code change requested.

- **007 cascade mechanics as shipped.** `.tool-out.is-ink, .sc-out.is-ink { animation: re-ink 160ms var(--ease-out); }` (site.css:427) is declared after `rise-in` (:421) with equal specificity, so re-runs correctly win; `re-ink` has no fill, so the panel settles to underlying opacity 1 and can never stick at .35; remove→reflow→re-add in one task restarts the animation, the transient `rise-in` name during the forced reflow cannot get a painted frame, and spam re-runs just re-dip from .35. - **007 reduced-motion path.** `.tool-out.is-ink, .sc-out.is-ink { animation: none; }` (site.css:1112) is declared after the RM `fade-in … both` list (:1110) and matches exactly the shipped mechanism; first reveal under RM fades, re-runs swap instantly; mid-session `prefers-reduced-motion` toggles in either direction resolve correctly with the sticky class (the hero-reel RM-flip spec's pattern is unaffected).
- **007 coverage of all re-runnable outputs.** `moleOut`/`skinOut`/`prepOut` carry `class="tool-out"` and `scOut` carries `class="tool-out sc-out"` (content/pages/tools.mjs:51,74,138,163), so both compound selectors in the new rules hit real elements and every `show()` target is styled; boundary respected — no `.is-ink` on `bk-status`/`bk-err`, and `say()` is untouched. Live-region semantics unchanged (`innerHTML` into the `role="status"` panel still announces; the dip is visual-only).
- **006 booking flow correctness.** `rerun` is sampled before any mutation (site.js:409 path); on success the JS order `turnstile.reset → fields.hidden = true → status.hidden = true → confirmBox.hidden = false → replaceChildren → confirmBox.focus({preventScroll:true})` (site.js:665–686) moves focus synchronously out of the fading fieldset, and the submit button stays `disabled` on success, so the 200 ms fading window has no re-submit path and no focus orphan. `fields` is never un-hidden anywhere in the codebase (grep-verified), so the entry direction (which lacks `@starting-style`) is unreachable.
- **006 RM handling is done right** — unlike the drawer: `.bk-form-fields[hidden]` (site.css:439) declares `opacity` only and no transition, so the RM list entry `.bk-form-fields` (site.css:1097, 0,1,0, later source than :438) genuinely kills both the opacity and display transitions; reduced motion restores the instant swap.
- **No `[hidden]` landmines.** site.css contains no global `[hidden] { display: none !important }` normalization and no author `display` rule on `.tool-q`/`.bk-form-fields` (`.tool-q` sets border/padding/margin only), so the UA `[hidden]` display change is free to participate in the `allow-discrete` transition.
- **011 exit idiom itself is the correct pattern** for no-preference users: `visibility 0s linear .3s` on the base (close: holds visible through the slide, then steps) and `0s linear 0s` on `.active` (open: instant visible + slide) — matching the admin-sheet precedent at public/css/style.css:1118/1125; rapid close→open retargets the transform transition cleanly; `.scrim`, `.burger`, `:root`, and the token set are untouched per boundaries, and `--ease-drawer`/`--ease-out`/literal 160ms/200ms match the estimator, `.mega`, and RM neighbours' house values; `@keyframes re-ink` colocated with its use mirrors `pkg-in`/`pkg-out`.
- **Markup/generator sync.** `content/pages/book.mjs:44` and `public/book/index.html:69` carry `class="tool-q bk-form-fields"` identically; no other page renders `#sbFields`; no unit test asserts the old class list (`grep tool-q|sbFields|bk-form` in tests/ — zero hits), and pages.test.mjs's build-output checks cover links/SEO/chambers only.
- **Existing e2e specs are timing-insensitive to these changes**: `toHaveClass(/active/)`, `not.toHaveClass`, `toBeVisible`/`toBeHidden` and click actionability all auto-retry well past 200/300 ms, `mobile-site.spec.mjs`'s focus-return assertion (`document.activeElement.id === 'burger'`) is unaffected by CSS stepping, and no spec opens the drawer under reduce (which is why the P1 escapes the suite, not a spec break).

Bottom line: two mechanisms are sound and one RM-list bookkeeping step was missed. The P1 fix is a one-line addition (`.drawer.active` into the reduce list) plus the P2 `inert` toggle decision; with those, this is shippable.
