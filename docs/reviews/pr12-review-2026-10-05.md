## PR #12 review — fix/slow-press-flake (f668c83)

**Verdict: approve**

The root cause is real and reproduced exactly as claimed, the new regression
spec is honest (12/12 fail on master's `site.js`, 12/12 pass on this branch,
preconditions verified instrumented), and the fix closes the hole without
changing the reduced-motion / no-View-Transitions paths. Edge-case probes found
no phantom-open path. Two nits and one pre-existing, non-blocking issue below.

### What I verified (with output)

1. **Root cause, reproduced on master** (`origin/master`, detached worktree
   `/tmp/review-master`, 66fe532). The "slow press" spec fails ~1/3 of runs:
   four `--repeat-each=15` batches gave failures `3+3+5+6 = 17/60`
   (`#pkgView` stayed hidden), consistent with the claimed ~9/45 flake.
   An instrumented probe running the same physical sequence (Escape, then a
   press that starts ~instantly and is held 900 ms so it straddles the ~440 ms
   close transition) passed on master but left the view hidden 8/8 with this
   event stream:
   ```
   VISIBLE: false EVENTS: ["pointerdown@HTML:","pointerup@BUTTON:…pr-card-book…","click@HTML:"]
   ```
   i.e. down on `<html>` (the VT overlay hit-tests everything), up on the
   card, click dispatched to their common ancestor `<html>` where no handler
   acted — the press is dropped. No other failure signature was produced.

2. **The new spec is honest.** Copied onto master (old `public/js/site.js`):
   `npx playwright test zz-newpress --repeat-each=12` →
   `12 failed`, all at the final assertion:
   ```
   Error: the press that straddled the transition opens the card
   > 31 |   await expect(view, 'the press that straddled the transition opens the card').toBeVisible();
   ```
   not on a precondition. On the branch it passes `12/12`. I also instrumented
   the spec (temporary probe copy) to assert the straddle actually happens:
   `.vt` was present at `mouse.down` on 4/4 runs (`VT-AT-DOWN: true`), and the
   event stream was `["pointerdown@HTML","pointerup@BUTTON","click@BUTTON","click@HTML"]`
   on the branch versus `["pointerdown@HTML","pointerup@BUTTON","click@HTML"]`
   on master. The extra `click@BUTTON` is the replay (Blink runs the
   microtask-deferred replay after the document capture listener that schedules
   it, which is why it logs before the stray `click@HTML`); master never
   produces it, so the spec cannot pass by skipping the straddle or via a
   native click. (Probe files were removed; worktrees left clean.)

3. **Handler edge cases.** Reasoned + probed:
   - A click whose target is genuinely `<html>` with `elementFromPoint`
     resolving to `<html>`/body is a no-op (`public/js/site.js:121-125`):
     the replay only calls `el.click()` when `el` is a real, non-`<html>`
     element. No-op, but also no phantom open.
   - Keyboard activation (Enter/Space) targets the button, never `<html>`, so
     the html-target replay branch is not reachable from the keyboard.
   - Touch scroll that starts on `<html>`: no click fires, so `pressedOnRoot`
     could persist — but every real click is preceded by a `pointerdown`,
     which re-primes the flag (`public/js/site.js:118`). A stale-true can only
     be consumed by a click with no pointerdown, which does not occur for
     pointer input, and the native-handler targets are never `<html>` in that
     case. No phantom open.
   - Double open / open-then-close: the original click targets `<html>`, so
     the `[data-pkg-open]` handler never sees it; the replay fires
     `el.click()` exactly once and the probed stream shows a single
     `click@BUTTON`. If the sheet is already open, `elementFromPoint` returns
     the dialog/backdrop, so the replay can't re-trigger `data-pkg-open`
     twice.
   - Press during the *opening* transition: the VT overlay still covers the
     viewport, so `elementFromPoint` resolves to `<html>` and the replay lands
     nowhere — the press is dropped, same as the pre-fix behaviour for clicks
     during a running transition. Not a regression.
   - Reduced motion / no View Transitions: `morph` short-circuits before
     `running` is assigned (`public/js/site.js:93-95`), so `running` is null
     and the pressedOnRoot path only triggers for clicks that genuinely target
     `<html>`; with no overlay there is no such click in practice. No change
     to those paths.

4. **CDP dependency.** `playwright.config.mjs` runs only the `chromium`
   project (`projects: [{ name: 'chromium', … }]`), so the
   `Animation.setPlaybackRate` CDP session works everywhere the suite runs.
   If a second engine project is ever added, this spec will throw on the
   CDP call and needs a guard — noted, not blocking.

### Findings

- **Should-fix (pre-existing, not introduced here — do not block this PR):**
  `public/js/site.js:102-107`. `morph`'s `t.finished.finally(...)` unconditionally
  removes `.vt`, clears `viewTransitionName`, and nulls `running` — including
  when `t` was aborted because a *newer* transition has already claimed those
  same properties (`document.startViewTransition` auto-aborts the previous
  one). That strips `.vt` / clears the name under a live transition →
  visual glitch (the newer sheet loses its captured snapshot). Suggested:
  only undo when this transition is still the current one:
  `t.finished.finally(() => { if (running !== t) return; view.classList.remove('vt'); … })`
  Also apply the same `to.style.viewTransitionName = ''` guard.

- **Nit:** a press that starts during the *opening* transition is dropped
  (see 3 above) because the replay can't land on a card while the overlay is
  up — acceptable, but `skipTransition()` on the open transition is a visible
  jump cut; if you ever want to keep the open animation honest for that
  gesture, gate the skip on `running !== null && transition-is-closing`.

- **Nit:** `public/js/site.js:118` — the capture-phase `pointerdown` listener
  is unconditional; a stale `pressedOnRoot` survives only up to the next
  pointerdown (see analysis), but a one-line guard (`e.isPrimary`) would make
  multi-touch edge behaviour explicit.
