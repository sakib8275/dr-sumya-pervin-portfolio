## v3 Immediate item 2 — token rotation — RECLASSIFIED, then defused

v3 said: *"Rotate the leaked `CLOUDFLARE_API_TOKEN` (`b17d8b13…`). Still unrotated, and a live

**That framing was wrong, and the correction matters.** The token was probed directly across

| Surface | Result |

| **R2 S3 API** — ListBuckets, ListObjects on `dr-sumya-gallery` | `403 AccessDenied` — **uninformative, see below** |

**It is an R2 API token, not a user API token.** The value carries the `cfut_` prefix, which
Cloudflare's own docs (`~/.claude/skills/cloudflare/references/r2-data-catalog/README.md:28`)
identify as the R2 API token format. That single fact explains everything that was confusing:

- **Why it could not be found in the dashboard.** R2 tokens live under
  **R2 → API → Manage API Tokens** (`dash.cloudflare.com/<account_id>/r2/api-tokens`), *not*
  My Profile → API Tokens. Searching the profile page for the id will always come up empty.
- **Why every v4 probe returned empty or `9109`.** R2 tokens do not authenticate against the
  account/zone/user endpoints at all. The empty `/accounts` list was never evidence of a narrow
  token — it was the wrong API surface.

### ⚠️ Blast radius is UNKNOWN — assume admin read/write on all R2 buckets

An earlier draft of this handoff claimed the S3 `AccessDenied` proved the token was recognised
but unpermissioned, and therefore could not touch `dr-sumya-gallery`. **That was wrong. Do not
rely on it.** A controlled retest:

| Test | Result |
|---|---|
| real AccessKeyId + SHA-256-derived secret | `AccessDenied` |
| real AccessKeyId + **deliberately wrong** secret | `AccessDenied` — **identical** |
| bogus AccessKeyId | `Unauthorized` — different |

Because a knowingly-bad signature produces the *same* `AccessDenied`, that error does not
distinguish "authenticated but unauthorised" from "bad signature". R2 collapses the two. The
SHA-256 derivation is also probably wrong for the `cfut_` format, so the request may never have
been correctly signed at all.

What the third row *does* establish: the access key `b17d8b1322d3a80ddeebb36d76ae8ba5` is
**recognised as a real key on this account** — a bogus one returns `Unauthorized` instead. So it
is one of the tokens listed under R2 → API → User API Tokens, and as of 2026-07-31 **both**
tokens there (`Edit Cloudflare Workers`, issued Jun 7 2026; `sakib-portfolio-v2 build token`,
issued Apr 17 2026) show **All buckets / Admin Read & Write**, both Active.

**Therefore assume the leaked token holds admin read/write on every R2 bucket, including
`dr-sumya-gallery`.** This is incident response, not hygiene. It cannot be proven either way
from this machine, and the available evidence points at broad access rather than none.

Also verified: the secret value appears **0 times** in the full git history (`git log --all -p`).
Only the token *id* is in committed docs, and an id is not a credential. The repo is **private**.

the variable is set. The safe form, used throughout this session:

