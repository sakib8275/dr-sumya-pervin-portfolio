## Findings this plan fixes

### F13 — HIGH · Settings form is unsaveable and `admin_email` is dead (X1)

The Settings tab's "Admin Reset Destination Email" field is load-bearing HTML that
no code touches:

| Evidence | Location |
|---|---|
| Field exists, `required` | `public/index.html:794-798` (`adminEmailInput`) |
| Never populated | `public/js/main.js:1494-1499` (`loadCMSConfigForm` fills only `doctorWaInput`/`doctorTgInput`) |
| Never read on submit | `public/js/main.js:1236-1264` (handler builds `body` from whatsapp/telegram/newPin/currentPin only) |
| Never served | `functions/api/config/index.js:6-16` (GET returns only `{whatsapp, telegram}`) |
| Never accepted | `functions/api/config/index.js:18-64` (PUT destructures only `whatsapp, telegram, current_pin, new_pin`) |

Two distinct symptoms, same root cause:

1. **The form cannot be saved.** Because the field is `required` and is never
   populated, the browser's native validation blocks the submit event until the
   admin types an email into it — no JS handler runs at all. An admin trying to
   change the doctor's WhatsApp number literally cannot press Save.
2. **The field lies.** Whatever email the admin *does* type is silently discarded;
   nothing is sent to the API. The only way `admin_email` changes today is operator
   SQL (`UPDATE admin_settings SET admin_email=…`).

**Why it matters beyond the form:** `forgot-password.js:27-28` gates the entire
reset path on `admin_email`. It is currently set only by the operator seed. And the
mailer hardcodes its recipient (`workers/mailer/mailer.js:4`,
`ALLOWED_RECIPIENT = 'dr.enamtalha@gmail.com'`), so any future value that is not a
Cloudflare Email-Routing-verified destination makes the reset *silently* not send
(HANDOFF-2026-08-05-self-service-cms.md:205 guardrail). The fix must therefore
both wire the field end-to-end **and** keep the verified-destination constraint
visible to the admin.

### F14 — LOW · CMS PIN input lacks `autocomplete` hardening

`public/index.html:600` — `cmsPinInput` has no `autocomplete` attribute, so
browsers offer to save/re-fill the PIN. This is the field Task 0's "related,
smaller" item names (`HUMAN-TASKS.md:79-81`) and the same vector that leaked the
PIN into a transcript on 2026-08-03. The two reset-form PIN fields (`resetNewPin`,
`resetConfirmPin`, index.html:868,872) have the same gap.

### F15 — INFO · no application-level login throttle (documented decision, no change)

`functions/api/auth/login.js:8-9` deliberately has no app-level throttle; the
comment notes a WAF rule cannot cover `pages.dev`. TOTP verification does have a
5-attempt lockout (`functions/api/auth/2fa/verify.js:28-34`). **No code change** —
the Turnstile-first ordering already blocks the fast-path brute force, and adding a
second throttle would duplicate a WAF rule once the domain is live. Recorded so a
future reader does not re-litigate it.

**Status 2026-08-05:** recorded, accepted — no change made, no follow-up pending.

## Fix specifications

### F13 — Wire `admin_email` through Settings, end-to-end

1. **`functions/api/config/index.js` — GET** (`:6-16`)
   - `SELECT whatsapp, telegram, admin_email …`; return
     `{ whatsapp, telegram, admin_email }`.
   - **Do not touch `functions/api/config/public.js`** — the uptime probe
     (F11) and `tests/config.test.mjs:15-28` assert `/api/config/public` returns
     *exactly* `{whatsapp, telegram}`; `admin_email` must never appear there.

2. **`functions/api/config/index.js` — PUT** (`:18-64`)
   - Destructure `admin_email` alongside the others.
   - If provided: must be a string, pass the same basic email regex the
     forgot-password path uses (`forgot-password.js:14`,
     `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`), and length ≤ 254; else 400 with a clear
     message (`'admin_email must be a valid email address'`).
   - Persist in **both** branches (with-PIN rotation and without), alongside the
     existing columns, in the same single UPDATE.
   - Log the change as `admin_email_set: <bool>` (never the address itself —
     the redaction contract in `functions/lib/log.js` treats the admin email as
     never-logged). Reuse the existing `config.update` event.

3. **`public/js/main.js`**
   - `loadCMSConfigForm()` (`:1494-1499`): also set
     `adminEmailInput.value = cmsConfig.admin_email || ''`.
   - Config form submit handler (`:1236-1264`): read `adminEmailInput`, include
     `admin_email` in `body` (empty string is a legal value — it clears the reset
     destination back to "unset", mirroring how `whatsapp: ''` already behaves).

4. **`public/index.html:794-798`**
   - Keep the field `required` and the helper text that says it must be a
     Cloudflare Email Routing **verified recipient** — with the API now
     populating it, an empty value no longer blocks unrelated saves, and the
     label tells the admin the real constraint before they change it. No other
     markup change.

5. **Tests — extend `tests/config.test.mjs`**
   - Admin GET returns `admin_email` (seed it first via `h.db`, as
     `tests/reset.test.mjs:27-31` does).
   - Admin PUT with a valid `admin_email` persists; a second admin GET reflects it.
   - Admin PUT with `admin_email: 'not-an-email'` → 400, DB unchanged.
   - Admin PUT with `admin_email: ''` clears it (GET returns `''`).
   - Regression guard: `/api/config/public` still returns **exactly** two keys
     even while `admin_email` is set — strengthens the existing
     `config.test.mjs:27` assertion.
   - Regression guard: PIN rotation path still works when `admin_email` is
     included in the same PUT body.

### F14 — `autocomplete` hardening on the three CMS PIN/email fields

- `public/index.html:600` — `cmsPinInput` → add `autocomplete="new-password"`
  (this is the field whose saved value leaked; `new-password` is what stops the
  browser offering to store it for reuse).
- `public/index.html:868` (`resetNewPin`) and `:872` (`resetConfirmPin`) → add
  `autocomplete="new-password"`.
- `public/index.html:844` (`forgotEmailInput`) → add `autocomplete="email"`.
- **Verify:** grep the served HTML for the four attributes; a manual browser pass
  confirms no save-PIN offer on the CMS login.

### F15 — no code; record only

  the workflows changes.
